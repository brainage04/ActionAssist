## Loader parity findings (2026-09-29)

From running the release NeoForge jar on a real NeoForge 26.2.0.41-beta server and client. Items marked *both loaders* come from shared code.

- [x] **Medium, 26.2:** no status message ever shows (start/stop, hand not empty, fewer than 3 free slots, no deposit container, container selected/cleared, vein key missing). `StatusMessages.java:39-53` looks up a `(Component, boolean)` player method by reflection; 26.2 has none, so it falls back to a single-`Component` method, which resolves to `Entity.setCustomName` and renames the local player instead.
  Fixed: `StatusMessages` calls a per-version `ActionBar` (`src/client-1.21`: `displayClientMessage(msg, true)`; `src/client-26`: `sendOverlayMessage(msg)`), no reflection; the platform GameTest asserts the F6 message reaches the action bar and does not rename the player.
- [ ] Low: the default F6 key conflicts with vanilla's debug options key.

- [x] Flaky platform GameTest: "Expected the vein-mining key held on every clicking tick" failed off by one tick (e.g. 234/235, 228/229) on random targets under load (1.21.1/1.21.4/26.1.2 NeoForge; seen locally three times and in CI on 2026-10-01).
  Cause: a test artefact. The observer only tracked deposits on observed ticks, so a deposit that began inside the 41-tick pause window went unseen; when it ended on the first observed tick, the chest close (`KeyMapping.setAll` on `setScreen(null)`) had released the vein key and the tick was counted. Fixed: `trackDeposits` runs on every running tick, including the pause window; reproduced by forcing that boundary on 1.21.1 NeoForge (2/2 failures before, 8/8 passes after; 3/3 on 26.2 Fabric with the scenario-before-macro listener order). Fabric development launches shuffle entrypoints; that order is not target-specific.
- [ ] Flaky platform GameTest: the 26.2 Fabric "inventory key opens the inventory screen" assertion failed once (2026-10-02 01:54, pause tick 3).
  Findings (2026-10-03, second investigation): the historical trigger remains unproved, so this item stays open. Two deterministic probes reproduced the exact tick-3 assertion: resetting the queued inventory click with vanilla `KeyMapping.releaseAll` (1/1 failure before, 1/1 full scenario pass after synchronous inventory opening), and closing the deposit chest then opening the player's inventory during `DEPOSIT_VERIFY` (1/1 failure before, 1/1 targeted pass after menu-identity ownership checks; the interrupted macro stops and leaves inventory open). The latter is a real mod bug but bypasses the scenario's tick-0 deposit guard, so it is not evidence of the original cause.
  Ruled out from 26.2 vanilla bytecode and macro transitions: `setAll`/`setDown(false)` do not clear `clickCount`; focus/mouse grab do not gate `handleKeybinds` once screen/overlay are absent; ordinary deposits cannot finish by pause tick 3. Fabric end-tick order varies with development entrypoint shuffling on every target; NeoForge registers the macro before the scenario. The pause driver now opens inventory synchronously and requires that exact screen through tick 20, with no retries, longer waits, or click tolerance. Deposits retain their opened menu and cannot transfer into or close a replacement screen.
  Loaded verification: client and four SHA256 workers pinned to CPUs 0–1; 5/5 full scenarios reaching inventory passed with seeded 0–1000 ms crop-frame stalls (three scenario-first, two macro-first), plus 4/4 uninstrumented full passes (two of each order). One additional stalled run stopped in the pebble phase with `DEPOSIT_UNREACHABLE` before inventory and is excluded from the inventory count (9 full passes / 10 total loaded launches). Temporary hooks removed; new evidence in `/tmp/aa-sol/inventory2-evidence/`. Previous unforced investigation: 16/16 inventory passes, evidence in `/tmp/aa-sol/inventory-evidence/`, plus ten earlier instrumented stall runs without reproduction.
  Final verification: `./gradlew --no-daemon build` passed (116 tasks, 72 executed); uninstrumented `platformGameTest` passed all 16 targets with identical outcomes in 18m 8s (159 tasks). A temporary init script only disabled Loom's automatic Xvfb to use display :331; it was removed afterwards.
- [x] Flaky platform GameTest under frame stalls: "Expected no right-clicks while a screen is open" (previously 2/29 failures on 26.1.2 NeoForge and 26.2 Fabric).
  Cause: server-side `uses` counted queued pre-screen packets after the tick-3 client baseline (396 → 398 with zero new client dispatches; reproduced 2/4 runs with seeded 0–260 ms frame stalls). Fixed: both loaders observe fixture-block uses on the client thread and latch any use with an actual screen open, from the inventory request onward; total client uses only prove resumption. This also excludes legitimate clicks after an early deposit close. Final stalled verification: 3/3 passes on 26.1.2 NeoForge and 3/3 on 26.1.2 Fabric; no click tolerance.
  Verification: a real click through inventory on pause tick 1 was rejected; an early screen close with legitimate resumed clicks passed. `./gradlew --no-daemon build` passed; the final uninstrumented combined `platformGameTest` passed all 16 targets with identical outcomes.

- [x] Flaky platform GameTest: "Expected the crosshair on the centre wheat" saw air and targeted the farmland before the crop macro started (26.2 Fabric, CI and local load on 2026-10-03).
  Cause: server-only `setupComplete` plus fixed client-tick waits raced block-update delivery; late planting also skipped the tick-10 `lookAt`. Fixed: bounded waits for client-visible lit farmland, all three wheat blocks, then the actual centre-wheat hit, with aiming in its own phase.
  Reproduction: with four SHA256 workers/client pinned to CPUs 0–1 and seeded 0–1000 ms frame stalls, a controlled 2500 ms server stall after planting/acknowledgement reproduced the exact air/farmland assertion (server tick 1636: wheat, light 15, survives; client ticks 10–11: air): 1/1 failure before, 3/3 full scenario passes after with the same load/stall/seed, aiming only once wheat became visible at ticks 42, 42, and 34. A separate 2500 ms pre-placement stall reproduced the missed aim at client tick 38 (1/1 failure before, 1/1 full pass after). Temporary tracing and stall injection removed; logs retained in `/tmp/aa-sol/wheat-evidence/`.
  Verification: after removing instrumentation, 3/3 standalone 26.2 Fabric scenarios and 1/1 embedded `:mc262Fabric:runClientGameTest` passed with the same four CPU-load workers/client pinned to CPUs 0–1 (no injected stalls); logs contain no tracing. `./gradlew --no-daemon build` passed on the uninstrumented fix (116 tasks up-to-date). The full `platformGameTest` passed all 16 targets with identical outcomes in 18m 15s (159 tasks); a temporary init script only disabled Loom's automatic Xvfb to use display :311, and was removed afterwards.
